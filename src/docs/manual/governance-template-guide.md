# 治理表格填写说明

## 功能概述

治理负责人从 **我的待治理清单** 下载治理表格（软件导入模板），按本说明逐列维护治理结果后回传。表格共 **23 列**，列名与顺序固定，请勿增删列或调整顺序，否则系统无法解析。

回传时系统按「必填项齐全、枚举取值合法、名称/版本与清单一致、表格内不重复、未与已入库重复」逐条校验，**任一条不通过则整份文件无法导入**。

> 建议先点「下载示例模板」参照填写格式，再点「下载该清单模板」在预填了软件名称/版本/托管地址的基础上补充其余字段。

## 填写总则

1. **23 列全部为必填**。确实没有内容的字段，请填 `无`，不要留空；JSON 类字段无内容时可填 `[]` 或 `无`。
2. **国内托管地址目前支持 AtomGit 平台地址**。源码原本就托管在 AtomGit 的，两个地址填同一个 AtomGit 地址；源码仅在 GitHub 等境外仓库的，请**先手动上传至 AtomGit**，再填写上传后的 AtomGit 地址。
3. **软件说明为 Markdown 格式**，支持标题、列表、代码块、表格、链接等语法。
4. 表头下**第 2 行起即为数据行**，请勿插入说明行、空行或合并单元格。
5. 日期建议统一为 `YYYY/MM/DD` 格式（如 `2026/3/26`）；无法确定具体日期时可填年份或 `无`。
6. 枚举列**必须从允许取值中选取**，不得自造词。枚举列共 8 项，取值分列在各列说明与「枚举速查」中：
- **列级枚举**：技术栈分类、集成风险、软件生命力；
- **JSON 字段内枚举**：漏洞风险等级（历史漏洞信息）、恶意类别 / 恶意类型 / 威胁等级 / 置信度（恶意代码）。

## 逐列填写说明

### 1. 软件名称

填写开源软件的名称，需与待治理清单中的名称一致。

- 示例：`requests`、`Spring Framework`、`Vue.js`
- 注意：名称与版本共同构成软件的唯一标识，两者都必须与清单一致，否则该行会被判定为「与所选清单不匹配」。

### 2. 软件版本

填写该软件的具体版本号，需与清单中的版本一致。

- 示例：`v2.0.1`、`18.2.0`、`3.4.21`
- 建议保留原始的 `v` 前缀，与清单保持一致即可。

### 3. 托管地址

填写软件的源码仓库原始托管地址，即代码的真实出处。

- 示例：`https://github.com/macournoyer/thin`
- 注意：此列是软件的原始出处，与下一列「国内托管地址」不是一回事。

### 4. 国内托管地址

**目前支持 AtomGit 平台地址**。分两种情况：

| 源码情况 | 填写方式 |
|---|---|
| 源码原本就托管在 AtomGit | 填写与「托管地址」**相同**的 AtomGit 地址 |
| 源码仅在 GitHub 等境外仓库 | 请**先手动上传至 AtomGit**，再填写上传后的 AtomGit 地址 |

- 示例（源码在 GitHub）：`https://atomgit.com/macournoyer/thin`
- 注意：填非 AtomGit 地址（如 GitHub、GitCode）会导致校验不通过；该地址是后续「源码备份」步骤拉取源码包的依据，地址错误会导致备份失败。

### 5. 源码包地址

填写该版本源码包（压缩包）的直接下载地址。

- 示例：`https://github.com/macournoyer/thin/archive/refs/tags/v2.0.1.zip`
- 无独立源码包时，可填写该版本的代码归档地址。

| Rel-MC | 安全组件 | 研发工具 | 媒体软件技术 |
| 数据压缩技术 | 分布式通信技术 | 编译器与编程语言技术 | WEB技术 |
| 分布式中间件 | 软件兼容性技术 | 虚拟化技术 | openstack |
| 操作系统技术 | 数据库技术 | 区块链技术 | 搜索技术 |
| 可编程逻辑 | NP | 光器件 | 能源 |
| 处理器 | 存储器 | 交换网 | 器件 |
| ADDA | 计算硬件网卡 | 安卓应用与框架 | 应用多媒体 |

| 云计算技术 | | | |

- 示例：`云计算技术`、`操作系统技术`、`数据库技术`

### 7. 集成风险

**枚举列**。评估该软件引入后对业务系统的集成风险等级，三选一：

`高`、`中`、`低`

- 判断参考：与现有技术栈冲突、改动量大、社区活跃度低、强耦合底层组件等，可评为「高」；接口清晰、可平滑替换、社区活跃、使用宽松类许可证的可评为「低」。

### 8. 主语言类型

填写该软件的主要开发语言。**该列不限制取值**，按实际情况填写即可。

- 示例：`Python`、`Java`、`C/C++`、`TypeScript`
- 注意：多语言项目填**占比最高**的那一种。

### 9. 开发商

填写软件的开发方，可以是个人、社区或公司。

- 示例：`Python Software Foundation`、`Apache`、`尤雨溪`、`Meta`
- 多个开发商可用 `、` 分隔；确实无明确主体的填 `无`。

### 10. 发布日期

填写**该版本**的发布日期，建议格式 `YYYY/MM/DD`。

- 示例：`2026/3/26`、`2026/1/1`

### 11. 来源地址

填写软件的官网或官方文档站点地址。

- 示例：`https://requests.readthedocs.io/en/latest/`
- 无独立站点时，可填写代码仓库主页地址。

### 12. CopyRight

填写版权声明列表，为 **JSON 数组**，每项包含声明所在文件与版权文本。

```json
[
  {"文件": "/src/requests/api.py", "copyright": "copyright (c) 2012 by Kenneth Reitz"},
  {"文件": "/LICENSE", "copyright": "Copyright 2019 Kenneth Reitz"}
]
```

- 建议由源码扫描工具（如版权检测）导出后粘贴，避免手工整理出错。

### 13. 千行代码量（KL）

填写代码规模，**只填数字**，单位为千行（KL）。

- 示例：`12`（表示 12 千行）
- 注意：列名已含单位，单元格内不要再重复写 `KL` 或 `（KL）`。

### 14. 软件生命力

**枚举列**。评估该软件当前所处的生命周期阶段，三选一：

`成熟期`、`衰退期`、`成长期`

| 取值 | 判断参考 |
|---|---|
| 成长期 | 版本迭代快、功能持续增加、社区活跃 |
| 成熟期 | 版本稳定、API 趋于固定、社区平稳 |
| 衰退期 | 维护停滞、issue 长期未响应、已推荐替代方案 |

### 15. 社区EOL日期

填写社区宣布停止维护（End of Life）的日期，无则填 `无`。

- 示例：`2021/11/1`

### 16. 版本描述

用一句话说明该版本的特点或变更。

- 示例：`A simple, yet elegant, HTTP library.`

### 17. 主许可证

填写该软件的主许可证名称。

- 示例：`Apache License 2.0`、`MIT License`、`BSD-3-Clause`

### 18. 软件说明

填写项目的说明文档，**必须为 Markdown 格式**。

- 支持语法：标题（`#`）、列表（`-`）、代码块（```）、表格、链接（`[文本](地址)`）、加粗（`**文本**`）等；
- 内容建议包含：项目简介、安装方式、核心特性、使用示例、参考文档链接；
- 多行内容直接在单元格内换行书写即可（按 `Alt + Enter` 在单元格内换行）。

Markdown 示例：

````markdown
# Requests

**Requests** 是一个简单而优雅的 HTTP 库。

## 安装

$ python -m pip install requests

## 核心特性

- Keep-Alive 与连接池
- 自动内容解压缩和解码
- 连接超时与流式下载

参考文档：https://requests.readthedocs.io
````

### 19. 依赖清单

填写该软件的组件依赖树，为 **JSON 数组**。每个组件包含组件名称、版本、编程语言，若有下级依赖则通过 `child` 字段嵌套（支持多级）。

```json
[
  {
    "组件名称": "yard",
    "版本": "0.9.28",
    "编程语言": "Ruby",
    "child": [
      {
        "组件名称": "yard-子组件示例A",
        "版本": "1.0.0",
        "编程语言": "Ruby",
        "child": [
          {"组件名称": "yard-三级示例A1", "版本": "0.5.0", "编程语言": "Ruby"}
        ]
      }
    ]
  },
  {"组件名称": "yardstick", "版本": "<1.0", "编程语言": "Ruby"}
]
```

- 无依赖或无法获取时填 `无`；
- 建议由 SBOM 工具（软件成分分析）导出，保证层级完整。

### 20. 历史漏洞信息

填写该软件已公开的历史漏洞，为 **JSON 数组**。

| 字段 | 说明 | 取值 |
|---|---|---|
| CVE编号 | 漏洞编号 | 如 `CVE-2009-3287` |
| 严重程度 | **枚举列**：漏洞风险等级 | `超危`、`高危`、`中危`、`低危` |
| CVSS评分 | CVSS 评分 | 0 ~ 10 的数字，如 `7.5` |

**漏洞风险等级枚举**：`超危`、`高危`、`中危`、`低危`

```json
[
  {"CVE编号": "CVE-2009-3287", "严重程度": "高危", "CVSS评分": 7.5},
  {"CVE编号": "CVE-2024-12345", "严重程度": "超危", "CVSS评分": 9.8}
]
```

- 无历史漏洞时填 `[]` 或 `无`；
- 系统会按此列统计「漏洞数」，其中含 `高危` / `超危` 的记录会将软件风险等级判为「高危」并影响评分。

### 21. 恶意代码

填写恶意代码检测结果，为 **JSON 数组**，无检出时填 `[]` 或 `无`。

| 字段 | 说明 | 取值 |
|---|---|---|
| 文件名称 | 检出所在文件/包名 | 如 `diff2html-3.4.47.tgz` |
| 文件位置 | 检出位置（包内路径） | 如 `package/package.json` |
| 恶意类别 | **枚举列** | 见下方「恶意类别枚举」 |
| 恶意类型 | **枚举列** | `恶意行为`、`恶意代码`、`恶意软件` |
| 恶意类型小类 | 具体行为（无固定枚举） | 见下方「恶意类型小类参考」 |
| 威胁等级 | **枚举列** | `超危`、`高危`、`中危`、`低危` |
| 置信度 | **枚举列** | `高`、`中`、`低` |
| 检测结果 | 检测引擎给出的结论 | 如 `Malicious Command Execute` |
| 关键日志 | 命中的关键代码/日志片段 | 可含换行 |

```json
[
  {
    "文件名称": "diff2html-3.4.47.tgz",
    "文件位置": "diff2html-3.4.47.tgz\\>/package/package.json",
    "恶意类别": "JS",
    "恶意类型": "恶意行为",
    "恶意类型小类": "恶意命令执行",
    "威胁等级": "中危",
    "置信度": "中",
    "检测结果": "Malicious Command Execute",
    "关键日志": "疑似恶意代码：\nline[59]: \"coverage:push\": \"curl -Ls https://coverage.codacy.com/get.sh | bash\","
  }
]
```

**恶意类别枚举**（检出文件的语言/类型类别）：

`Java`、`JavaScript`、`JS`、`TypeScript`、`C/C++`、`C`、`C#`、`Python`、`Go`、`Rust`、`Ruby`、`PHP`、`Shell`、`PowerShell`、`Perl`、`Binary`、`Other`

**恶意类型枚举**：

`恶意行为`、`恶意代码`、`恶意软件`

**恶意类型小类参考**（无固定枚举，按行为归类）：

| 分类 | 取值 |
|---|---|
| 下载执行类 | 木马下载执行、恶意命令执行、反弹 Shell |
| 窃密类 | 信息窃取、敏感信息外发、密钥窃取 |
| 利用类 | 反序列化利用、命令注入、远程代码执行 |
| 权限类 | 权限提升、注册表篡改、计划任务创建 |
| 驻留类 | 后门驻留、Webshell、启动项持久化 |
| 资源类 | 恶意挖矿、资源耗尽 |
| 混淆类 | 代码混淆、编码隐藏、加壳 |

**威胁等级枚举**：`超危`、`高危`、`中危`、`低危`

**置信度枚举**： `高`、`中`、`低`

- 系统会按此列统计「恶意代码数」，检出恶意代码会将软件风险等级判为「高危」并影响评分。

### 22. 开发者信息

填写核心开发者信息，为 **JSON 数组**。

```json
[
  {"开发者名称": "lemoinem", "国家或地区": "美国", "组织或公司": "示例公司A"},
  {"开发者名称": "zaphod42", "国家或地区": "乌克兰", "组织或公司": "示例公司C"},
  {"开发者名称": "snaury", "国家或地区": "无", "组织或公司": "无"}
]
```

- 字段：`开发者名称`、`国家或地区`、`组织或公司`；
- 国家或地区、组织或公司不明确时填 `无`。

### 23. 许可证列表

填写该软件包含的许可证清单，为 **JSON 数组**。

```json
[
  {"许可证名称": "Apache License 2.0", "许可证类型": "apache", "是否批准": "已批准"},
  {"许可证名称": "MIT License", "许可证类型": "mit", "是否批准": "已批准"}
```

- 字段：`许可证名称`、`许可证类型`（小写标识，如 `apache`、`mit`、`bsd`、`gpl`）、`是否批准`（`已批准` / `待批准` / `未批准`）；
- 无许可证信息时填 `无`。

## 常见问题

**Q：某个字段确实没有内容，能留空吗？**

A：不能。23 列全部必填，没有内容的请填 `无`；JSON 类字段无内容时可填 `[]` 或 `无`。

**Q：JSON 字段格式写错了会怎样？**

A：系统按 JSON 解析，格式错误会导致该字段内容无法识别（如「依赖清单」解析失败则组件数按 0 计）。建议由扫描工具导出后直接粘贴，不要手工拼写引号和逗号。

**Q：国内托管地址填了 GitHub 地址，为什么回传不通过？**

A：国内托管地址目前支持 AtomGit 平台。请先将源码手动上传至 AtomGit，再填写上传后的 AtomGit 地址。

**Q：托管地址和国内托管地址有什么区别？**

A：托管地址是软件源码的原始出处（通常是 GitHub 等境外仓库），国内托管地址是国内的 AtomGit 备份位置，供平台后续拉取源码包使用。源码原本就在 AtomGit 时两者相同。

**Q：千行代码量为什么只填数字？**

A：该列列名已含单位「（KL）」，单元格内只填数字即可（如 `12`），不要再写 `KL`。

**Q：主语言类型有取值限制吗？**

A：没有。主语言类型不是枚举列，按实际情况填写该软件的主要开发语言即可；技术栈分类、集成风险、软件生命力等枚举列才需要从允许取值中选取。

**Q：枚举列填了列表以外的值会怎样？**

A：该行会被判定为「取值不在允许范围内」，整份文件无法导入。请从各列说明或「枚举速查」中选取。

**Q：软件说明必须用 Markdown 吗？**

A：是。该列按 Markdown 渲染展示，直接写纯文本也能显示，但使用 Markdown 语法（标题、列表、代码块）可获得更好的阅读效果。

**Q：名称和版本与清单不一致会怎样？**

A：该行会被判定为「与所选清单不匹配」，整份文件无法导入。请确保名称与版本和下载的清单模板完全对应。
